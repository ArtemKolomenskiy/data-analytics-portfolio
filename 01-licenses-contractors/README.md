# Дашборд «Лицензии контрагентов»

[Открыть дашборд](licenses_contractors.html) · [Посмотреть ноутбук](licenses_contractors.ipynb)

## Проблема бизнес-заказчика

Раньше контроль истекающих лицензий велся вручную: руководители отделов продаж раз в две недели открывали в 1С карточку каждой компании по очереди и вручную переносили информацию по каждому клиенту в отдельный Excel-файл.

Бизнес-заказчик столкнулся со следующими проблемами:

Потеря времени: регулярный ручной сбор, обновление и сверка данных отнимали у руководителей много времени.

Недостоверные данные: в процессе переноса руководители могли допускать ошибки, из-за чего решения принимались на основе некорректной информации.

Неправильная расстановка приоритетов: руководителям было неясно, на каких клиентах сфокусироваться в первую очередь, чтобы успеть продлить лицензии.

Упущенная выгода: зачастую менеджеры связывались с клиентами слишком поздно, из-за чего клиенты успевали уйти к конкурентам, а компания теряла деньги.

Эти проблемы указали на необходимость автоматизации процесса за счёт создания аналитической панели, которая подтягивает данные из 1С, собирает их в одном месте и помогает бизнес-заказчику принимать стратегические решения.

## Решение

Я разработал интерактивный дашборд, который агрегирует данные по истекающим в ближайшие 2 месяца лицензиям на программные продукты.

* В дашборде использованы синтетические данные, сгенерированные для демонстрации
Ключевые фичи дашборда:

В KPI-блоках руководитель видит четыре ключевых показателя: "Лицензий истекает" (в ближайшие 2 месяца), "Сумма в зоне риска", "Срочных (≤30 дней)" и "Сумма срочных". Бизнес-заказчик сразу получает ответ на вопрос: сколько лицензий и на какую сумму требует внимания прямо сейчас.

Два столбчатых графика показывают распределение истекающих лицензий по менеджерам: слева - количество, справа - сумма. Сортировка по убыванию позволяет бизнес-заказчику сразу увидеть нагрузку по команде: у кого из менеджеров больше всего клиентов в зоне риска и на какую сумму.

Сводная таблица помогает руководителю увидеть, кто из менеджеров отвечает за клиента, лицензия на какой продукт у него истекает и на какую сумму. Цветовая индикация дат окончания лицензий сразу дает понять, с какими клиентами нужно связаться в первую очередь.

## Сценарии использования стейкхолдерами

Дашборд предназначен для руководителя отдела продаж.

Задача: раз в 2 недели просмотреть все лицензии, истекающие в ближайшие 2 месяца, и расставить приоритеты в продлениях так, чтобы менеджеры в первую очередь занимались клиентами с крупными суммами и поджимающими сроками, а не разбирали список в произвольном порядке.

Сценарий использования:

Раз в 2 недели руководитель отдела продаж открывает дашборд и видит компании, у которых до истечения лицензии осталось менее 2 месяцев.

Далее он последовательно фильтрует лицензии по сумме в порядке убывания:

- свыше 500 000 руб.;
- от 300 000 до 500 000 руб.;
- от 100 000 до 300 000 руб.;
- менее 100 000 руб.
Для каждого диапазона с помощью цветовой индикации руководитель оценивает состояние лицензий по каждому менеджеру и приоритезирует задачи.

Затем ставит конкретным менеджерам задачи в CRM (например, "Связаться с ООО "Альфа" и предложить продлить лицензию)

Далее руководитель отдела продаж контролирует выполнение этих задач.

## Техническая реализация

Проект реализован последовательно из 4 этапов, где каждый следующий опирается на результат предыдущего. Сначала генерируются синтетические данные - набор из пяти таблиц, имитирующих реальную базу. На их основе собирается одна плоская денормализованная витрина данных. Из витрины затем строится многомерная сводная таблица и агрегаты, после чего данные отображаются в формате визуализаций в дашборде с помощью HTML.

### Первый этап - генерация синтетических данных

Сгенерированные в рамках 1-го этапа данные представляют собой 5 таблиц: licenses (таблица с информацией по лицензиям компаний на программные продукты), heads (справочник по руководителям отделов продаж), managers (справочник по менеджерам), companies (справочник по компаниям-клиентам), products (справочник по продуктам). Связи между таблицами заданы только через внешние ключи - данные имитируют реальную базу данных.

### Второй этап - построение витрины данных

В рамках 2-го этапа строится плоская денормализованная таблица detail, где одна строка соответствует одной активной лицензии, истекающей в ближайшие два месяца.

Витрина собирается с помощью четырёх merge (licenses -> companies -> managers -> heads -> products) с параметром validate='many_to_one', который гарантирует уникальность ключа в каждом справочнике и защищает от случайного размножения строк.

Затем применяется фильтр актуальности по трём условиям (start_date <= today, end_date >= today, end_date < deadline) и дедупликация по паре компания-продукт: сортировка по end_date и keep='first' оставляют из конкурирующих лицензий ту, что истекает раньше - именно её менеджер должен продлить в первую очередь.

### Третий этап - построение агрегатов и сводной таблицы для дашборда

В рамках третьего этапа на основании плоской таблицы detail строятся многомерная сводная таблица и набор агрегатов.

Используется pd.pivot_table с aggfunc='first': поскольку после дедупликации на пару "компания-продукт" остаётся ровно одна лицензия, агрегация сводится к выбору значения.

Строки образуют иерархию "руководитель -> менеджер -> продукт", столбцы - иерархию "метрика -> компания" (показатели представляют собой дату начала лицензии , дату окончания лицензии, сумму лицензии).

После pivot_table уровни столбцов идут в порядке "метрика -> компания", а нужно наоборот. swaplevel(0, 1, axis=1) меняет уровни местами, чтобы сверху была компания, а под ней - три метрики, а sort_index упорядочивает столбцы сначала по компаниям, затем по метрикам.

Метод reindex достраивает таблицу до полного прямоугольника "все компании + все три метрики" (fill_value=pd.NaT для пустот), чтобы у каждой компании всегда было одинаковое число столбцов.

Для остальных визуализаций на основании витрины detail строятся агрегированные таблицы и показатели:

Сначала создаётся dash - копия витрины с добавленным полем days_left (число дней до окончания лицензии.

На его основе считаются KPI-метрики: total_lic (общее количество истекающих лицензий), total_amt (сумма истекающих лицензий), urgent_lic и urgent_amt (количество и сумма лицензий, истекающих в ближайшие 30 дней).

Затем через groupby(['sales_head', 'manager']) с агрегатами licenses=('license_id', 'count'), amount=('amount', 'sum'), min_days=('days_left', 'min') строится by_manager - сводка по менеджерам с количеством и суммой их истекающих лицензий.

Из неё формируются два отсортированных датафрейма: by_manager_count (по убыванию количества лицензий) и by_manager_amount (по убыванию суммы) - на их основании строятся столбчатые графики в дашборде.

### Четвёртый этап - оформление агрегатов и сводной таблицы в формате визуализаций в дашборде.

На этом этапе агрегаты и сводная таблица превращаются в готовые визуальные блоки дашборда:

Функция kpi_card собирает HTML-карточку из трёх элементов: заголовок (kpi-title), крупное значение (kpi-value) и подпись (kpi-sub), плюс параметр accent для цвета акцентной полосы слева. Четыре плитки объединяются в сетку .kpi-grid: "Лицензий истекает", "Сумма в зоне риска", "Срочных (≤30 дней)", "Сумма срочных". Значения берутся из заранее построенных агрегатов (total_lic, total_amt, urgent_lic, urgent_amt).

В функции bar_chart  для каждой строки датафрейма вычисляется ширина бара как процент от максимума (pct = value / max_val * 100) и генерируется HTML bar-row - подпись слева, дорожка с заливкой и числом по центру справа. Вызывается дважды - для количества (by_manager_count) и суммы (by_manager_amount) лицензий по менеджерам, оба помещаются в .charts-grid.

С помощью функции date_cell_html даты окончания лицензии в сводной таблице дополнительно стилизуются цветом по числу дней до истечения: <15 - красный, 15–29 - оранжевый, ≥30 - зелёный.

## Бизнес-эффект

Экономия времени: сокращены трудозатраты руководителей отдела продаж на подготовку обзора истекающих лицензий.
